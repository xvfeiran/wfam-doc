# 7.4.2 定时任务型通知 — 分步测试操作手册

> 本手册把"等 13/21/3 天"压缩成"每条用例 ≤ 1 分钟"。原理：所有阈值/频率/cron 都是 yml 配置项，判定基准是数据库字段 `APMS_PART.STATUS_CHANGED_AT`，频率去重靠 `APMS_NOTIFICATION_LOG.SENT_AT`。改配置 + 改两个时间戳即可。
>
> 适用范围：用例 **429 / 430 / 431 / 431A / 432 / 433 / 434 / 435 / 436 / 437 / 438 / 439**。
> 用例 **435 / 436 / 437**（审批超期提醒）在 **v5.3 已修复**（原误查 Part 表 `pending_approval`，现改查 `AnalysisOrder`，按批次 `ANALYSIS_ORDER_ID` 去重）。修复后操作见 §4。

## 0. 核心机制速查（看懂这一节，后面都是机械操作）

| 控制点 | 代码位置 | 含义 |
|---|---|---|
| 定时入口 | `NotificationService.scheduledNotificationCheck()` `:108` | cron 触发，依次跑预警/超期/审批三段 |
| 预警判定 | `sendWarningNotifications()` `:121` | `STATUS='in_detailed_analysis'` 且 `warningDays ≤ 已等待天数 < overdueDays` |
| 超期判定 | `sendOverdueNotifications()` `:144` | `STATUS='in_detailed_analysis'` 且 `已等待天数 ≥ overdueDays` |
| 审批判定 | `sendApprovalReminderNotifications()` `:171` | `STATUS='pending_approval'`（**当前永不命中，缺陷**） |
| 频率去重 | `shouldSkip()` `:197` | 同 `PART_ID + NOTIFICATION_TYPE` 在 `frequency` 天内有 SENT 记录则跳过 |
| 邮件发送 | `EmailService.dispatch()` `:41` | **虚拟线程异步**，失败被 catch 吞掉 |
| 落库 | `sendAndLog()` `:204` | 发送（实际是 dispatch 启线程）后立即写 `STATUS=SENT` |

**观测判据（关键）**：`sendAndLog` 采用**同步发送**，按真实 SMTP 返回结果落库：全部成功 → `STATUS=SENT`，任一失败 → `STATUS=FAILED` + `ERROR_MESSAGE`。**只要定时任务命中条件（且未被去重跳过），`APMS_NOTIFICATION_LOG` 必有新记录**（SENT 或 FAILED），判通过看日志表即可。频率去重（`shouldSkip`）只认 `STATUS=SENT`，因此 **`FAILED` 记录在下一轮 cron 会自动重试**——这是 v5.2 的修复点，避免发送失败的通知被永久丢弃。

**预警窗口的坑（v3.18 修改后）**：预警只在 `[warningDays, overdueDays)` 区间发。`warningDays` 与 `overdueDays` 都配 0 时窗口为空集，预警永不触发——所以测预警时**必须让 `warningDays < overdueDays`**（见配置 A）。

## 1. 一次性环境准备

### 1.1 后端 yml 临时覆盖（`backend/src/main/resources/application-local.yml`）

在 `custom.notification` 节点下覆盖以下值。**分两套配置，按当前要测的用例组切换**。

#### 配置 A — 测预警 + 超期后不发预警（用例 429 / 430 / 431 / 431A）

```yaml
custom:
  notification:
    cron: "*/30 * * * * ?"          # 每 30 秒跑一次（Spring 6 位 cron 含秒）
    analysis:
      warning-days: 0               # 预警下界
      overdue-days: 2               # 超期下界 → 预警窗口 = [0, 2) 天
    frequency:
      warning: 1
      overdue: 1
```

#### 配置 B — 测超期 + 日志 + 失败（用例 432 / 433 / 434 / 438 / 439）

```yaml
custom:
  notification:
    cron: "*/30 * * * * ?"
    analysis:
      warning-days: 0
      overdue-days: 0               # 任何过去时间都满足超期
    frequency:
      warning: 1
      overdue: 3                    # 测 433/434 需要 3 天频率
```

### 1.2 关 AEP、开 Mock 邮箱（避免依赖外部 AEP/SMTP）

`application-local.yml` 顶部：

```yaml
aep:
  proxy:

    mock-qmc-leader-emails: "<你的邮箱>@cn.bosch.com"   # 超期/审批邮件的 QMC Leader 抄送走这里

      lisi: "<你的邮箱>@cn.bosch.com"                   # analyst 字段填 lisi 时，邮件发到这里
```

### 1.4 准备一条"被测 Part"

先看有没有现成可用的：

```sql
SELECT ID, PART_NUMBER, ANALYST, STATUS, STATUS_CHANGED_AT
FROM   APMS_PART
WHERE  STATUS = 'in_detailed_analysis'
  AND  ROWNUM <= 5;
```

- **有**：记下其中一个 `ID`（下文记作 `<PART_ID>`），确认 `ANALYST` 是 `user-emails` 里映射过的 loginName（不是就 UPDATE 一下）。
- **没有**：随便挑一条 part 改成被测状态：
  ```sql
  UPDATE APMS_PART
  SET    STATUS          = 'in_detailed_analysis',
         STATUS_CHANGED_AT = SYSDATE - 1,
         ANALYST          = 'lisi'
  WHERE  ID = '<挑一个 ID>';
  COMMIT;
  ```

## 2. 通用 SQL（反复用，建议存成 snippet）

```sql
-- 看某件最近的通知记录
SELECT PART_ID, NOTIFICATION_TYPE, RECIPIENTS, CC_RECIPIENTS, STATUS, SENT_AT, ERROR_MESSAGE
FROM   APMS_NOTIFICATION_LOG
WHERE  PART_ID = '<PART_ID>'
ORDER  BY SENT_AT DESC;

-- 重置去重（每条用例之间必须执行，否则 shouldSkip 会跳过）
DELETE FROM APMS_NOTIFICATION_LOG WHERE PART_ID = '<PART_ID>';
COMMIT;

-- 把某件"已等待天数"调到 N 天前
UPDATE APMS_PART SET STATUS_CHANGED_AT = SYSDATE - <N> WHERE ID = '<PART_ID>';
COMMIT;
```

> Oracle `SYSDATE - N` 单位是天，支持小数（`SYSDATE - 0.5` = 12 小时前）。

### 用例 429 — 预警通知触发  ✅ 使用【配置 A】

| 步骤 | 操作 |
|---|---|
| 1 | 套用配置 A，确保 `warning-days=0`、`overdue-days=2` |
| 2 | `DELETE FROM APMS_NOTIFICATION_LOG WHERE PART_ID='<PART_ID>'; COMMIT;` |
| 3 | `UPDATE APMS_PART SET STATUS_CHANGED_AT = SYSDATE - 1 WHERE ID='<PART_ID>'; COMMIT;`（已等 1 天，落在预警窗口 [0,2)） |
| 4 | 等 ≤ 30 秒（下一轮 cron） |
| 5 | 查日志表（见 §2 第 1 条） |

**预期**：新增一条 `NOTIFICATION_TYPE='WARNING'`、`RECIPIENTS` 含 lisi 邮箱、`STATUS='SENT'` 的记录；**无** `OVERDUE` 记录。

### 用例 430 — 预警频率 1 天/次（隔天再发）  ✅ 使用【配置 A】

| 步骤 | 操作 |
|---|---|
| 1 | 在 429 已发基础上（日志里有一条 WARNING） |
| 2 | 把这条日志的 `SENT_AT` 改成 2 天前，模拟"上次发送已超过 1 天频率窗口"：<br>`UPDATE APMS_NOTIFICATION_LOG SET SENT_AT = SYSDATE - 2 WHERE PART_ID='<PART_ID>' AND NOTIFICATION_TYPE='WARNING'; COMMIT;` |
| 3 | 等 ≤ 30 秒 |
| 4 | 查日志表 |

**预期**：新增**第二条** `WARNING/SENT` 记录（`shouldSkip` 因上次 SENT_AT 已超出 1 天窗口而放行）。

### 用例 431A — 超期后不再发预警（v3.18 新增）  ✅ 使用【配置 A】

### 用例 439 — 发送失败不中断定时任务  ✅ 使用【配置 B】

> v5.2 行为变更：原"异步发送、失败仍记 SENT、不重试"已改为"同步发送、失败记 FAILED、下轮自动重试"。本用例验证新行为。

| 步骤 | 操作 |
|---|---|
| 1 | 通过"邮件配置"页面（或直接 UPDATE `APMS_EMAIL_CONFIGURATION`）把 SMTP **密码**故意改错（或 host 改成连不上地址），保存 |
| 2 | `DELETE FROM APMS_NOTIFICATION_LOG WHERE PART_ID='<PART_ID>'; COMMIT;` |
| 3 | （配置 B 下 `overdue-days=0`，无需改 `STATUS_CHANGED_AT`；只要该件还在 `in_detailed_analysis`） |
| 4 | 等 ≤ 30 秒，盯后端控制台 |
| 5 | 查日志表，**确认本轮 `STATUS=FAILED`** |

**预期（本轮 = 失败）**：
- 后端控制台打印 `[email] Failed to <邮箱>: ...`（每个收件人/CC 一行；原 `[email-vt]` 前缀已随异步虚拟线程移除，现为同步发送的 `[email]`）；
- 定时任务**整体不崩溃**，下一轮 `Scheduled notification check started/completed` 照常出现；
- `APMS_NOTIFICATION_LOG` 新增一条 **`STATUS='FAILED'`**、`ERROR_MESSAGE` 非空（含地址 + 错误信息）。

**预期（下一轮 cron = 自动重试）** —— v5.2 核心验证点：
- 把 SMTP 密码/host **改回正确值**，保存；
- 等下一轮 cron（≤30 秒）；
- 由于 `shouldSkip` 只认 SENT、上轮 FAILED 不计入去重，本轮**再次发送**：控制台 `[email] Sent to ...`；
- `APMS_NOTIFICATION_LOG` 新增一条 `STATUS='SENT'`、`ERROR_MESSAGE=NULL`；
- 此后进入正常 3 天频率去重。

## 4. v5.3 已修复：435 / 436 / 437 — 审批超期提醒

> **历史缺陷（v5.3 前）**：`sendApprovalReminderNotifications` 原查询 `partRepository...findByStatusAndStatusChangedAtLessThanEqual("pending_approval", ...)`，但 `pending_approval` 是 **AnalysisOrder（批次）** 的状态、Part 永不处于该状态，查询永远返回空，审批提醒一封都发不出。
>
> **v5.3 修复**：改为查 `AnalysisOrder`（`status='pending_approval' AND statusChangedAt <= threshold`），按批次（`ANALYSIS_ORDER_ID`）维度去重；`APMS_NOTIFICATION_LOG` 新增 `ANALYSIS_ORDER_ID` 列、`PART_ID` 放宽为可空。收件人仅 QMC Leader，邮件显示退货单号 + 分析师 + 等待天数。

审批提醒是**批次维度**（不是 Part 维度），所以 SQL 操作对象是 `APMS_ANALYSIS_ORDER`。`<AO_ID>` 全程用同一个被测批次 ID。

### 用例 435 — 审批提醒触发

前置：`application-local.yml` 的 `custom.notification.analysis` 保持现状即可（审批用的是 `approval.overdue-days`，默认 3；本地可临时设 `approval.overdue-days: 0` 让任何过去时间都满足）。改完需重启后端生效。

| 步骤 | 操作 |
|---|---|
| 1 | 挑一个被测批次：<br>`SELECT ID, ORDER_ID, ANALYST, STATUS, STATUS_CHANGED_AT FROM APMS_ANALYSIS_ORDER WHERE ROWNUM <= 5;`，记下 `<AO_ID>` 和原 STATUS |
| 2 | 清空该批次的审批提醒日志（去重依据）：<br>`DELETE FROM APMS_NOTIFICATION_LOG WHERE ANALYSIS_ORDER_ID = '<AO_ID>'; COMMIT;` |
| 3 | 把批次置为 pending_approval 且超期：<br>`UPDATE APMS_ANALYSIS_ORDER SET STATUS='pending_approval', STATUS_CHANGED_AT = SYSDATE - 4 WHERE ID='<AO_ID>'; COMMIT;`（> approval-overdue-days=3） |
| 4 | 等 ≤30 秒下一轮 cron |

**预期**日志：
```
APPROVAL scan: candidateCount≥1, ...
APPROVAL check: analysisOrderId=<AO_ID>, orderId=..., analyst=..., ...
Notification dispatched: type=APPROVAL_REMINDER, partId=null, analysisOrderId=<AO_ID>, recipients=<QMC Leader 邮箱>, status=SENT
```
收到审批提醒邮件（主题含退货单号 + 等待天数）。

### 用例 436 — 审批频率未满 3 天（不再发）

紧接 435，**不改任何东西**，再等一轮 cron。

**预期**：`APPROVAL skip (within frequency window 3d): analysisOrderId=<AO_ID>`，无 dispatched、无新邮件。

> 测"超 3 天再发"：把上次 APPROVAL_REMINDER 的 `SENT_AT` 改 `SYSDATE - 4` 后等一轮，应再次 dispatched（与超期频率 433 同构）。

### 用例 437 — 审批完成后不再提醒

```sql
UPDATE APMS_ANALYSIS_ORDER SET STATUS = 'approved' WHERE ID = '<AO_ID>';
COMMIT;
```

等一轮 cron。**预期**：该批次不在候选集（`candidateCount` 不含它），无 dispatched。

### 收尾
